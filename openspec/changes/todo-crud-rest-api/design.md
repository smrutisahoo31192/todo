## Context

The project is a FastAPI application (`app/main.py`) with a single `GET /health` endpoint and no data persistence layer. The goal is to add a full CRUD REST API for todo items. The codebase is minimal (greenfield), so we can introduce clean module structure without migration concerns.

FastAPI ships with Pydantic v2 as its validation engine, so no new runtime dependencies are required.

## Goals / Non-Goals

**Goals:**
- Expose five REST endpoints covering the full todo lifecycle: list, create, read, update (full and partial), delete
- Pydantic schemas for request validation and response serialization
- Proper HTTP error semantics: 404 for missing items, 422 for invalid payloads (handled automatically by FastAPI/Pydantic)
- Organized module layout that keeps `main.py` thin

**Non-Goals:**
- Persistent database storage (deferred to a future ticket)
- Authentication/authorization
- Pagination, filtering, or sorting of the todo list
- Soft-delete semantics

## Decisions

### 1. Module layout: router + schemas + storage as separate modules

**Decision**: Split into `app/routers/todos.py`, `app/schemas.py`, and `app/storage.py`.

**Rationale**: A single `main.py` monolith would quickly become unreadable. Separating concerns (schemas, storage, route handlers) follows FastAPI's documented best-practice layout and makes each module independently testable. The storage module can later be swapped for a real database adapter without touching routes or schemas.

**Alternatives considered**:
- Everything in `main.py` — rejected; too cramped for five endpoints + schemas
- SQLite via SQLModel — deferred; out of scope for this ticket

### 2. In-memory storage via a module-level list + counter

**Decision**: `app/storage.py` maintains a `list[dict]` and an `int` counter as module-level state. Helper functions (`get_all`, `get_by_id`, `create`, `update`, `delete`) provide a clean interface.

**Rationale**: Keeps the implementation self-contained with zero dependencies. Tests can reset the store between runs by clearing the list and resetting the counter.

**Alternatives considered**:
- Class-based singleton — more boilerplate for identical behaviour
- Redis or sqlite3 in-memory — over-engineered for this iteration

### 3. PUT performs a full replacement; PATCH performs a partial update

**Decision**: `PUT /todos/{id}` requires both `title` and `completed` fields; `PATCH /todos/{id}` accepts either or both via a schema with all-optional fields.

**Rationale**: This aligns with RFC 7231 (PUT = replace) and RFC 5789 (PATCH = partial update). Both are listed in the acceptance criteria.

### 4. 404 via `HTTPException`, 422 auto-generated by FastAPI

**Decision**: Route handlers raise `HTTPException(status_code=404)` when an item is not found. 422 responses for malformed JSON or schema violations are produced automatically by FastAPI's request validation layer.

**Rationale**: No custom exception middleware needed; FastAPI handles 422 out-of-the-box.

## Risks / Trade-offs

- **Data loss on restart**: In-memory store is ephemeral. → Mitigation: Acceptable for this iteration; database persistence is a planned follow-up.
- **Concurrency**: Module-level list is not thread-safe under Uvicorn's multi-worker mode. → Mitigation: Single-worker deployment is assumed for now; locking or an external store would be required for production.
- **Test isolation**: Tests must reset the store before each test case to avoid state bleed. → Mitigation: Expose a `reset()` helper in `storage.py` and call it in a `setup_function` or fixture.
